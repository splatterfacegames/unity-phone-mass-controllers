A pure-C# package for Unity

Turn a Unity game into the host for a room full of phone controllers.

Players scan a QR code on the big screen; their phone's browser loads a controller page served by the game itself. No app install, no Node, no relay server, no native binaries. Jackbox-style, with the game as the authority.

How it works

1

Add the component

Install the UPM package, then Add Component → Splatter → Phone Mass Controllers on a GameObject and point ControllerDir at a folder of plain HTML/JS — your controller page.

2

Show the QR on screen

host.QrTexture() renders a join QR in pure C#. Put it on a RawImage next to host.Host.JoinUrl() for the rare manual typist. Works in Play mode and edit mode.

3

Phones join via browser

The camera app scans the code, the game serves the page, and a WebSocket opens on the same port. From then on they're players — named, rejoinable, kickable — not raw sockets.

What's in the box

One port, HTTP + WebSocket

Its own RFC 6455 server on raw sockets — masking, fragmentation, ping/pong, binary frames — with a dedicated I/O thread and a per-Poll() drain budget, so a slow phone can't stall the game. The same port serves your page, the SDK, the QR PNG and the socket, so a single tunnel hostname works. No dependencies.

Players, not sockets

Random 128-bit rejoin tokens, a grace period for drops, and tombstones that restore a returning player's id and Meta. Join codes, max players, kick/ban, "replaced by another tab" detection, and PIN-gated admin — the lobby bookkeeping a party game actually needs.

Private by default

host.Send(player, data) targets one phone; host.Broadcast(data, filter) reaches the rest. JSON via JToken for convenience, or raw byte[] frames passed through untouched — FlatBuffers-friendly for big payloads.

QR encoder built in

PmcQr is a pure-C# QR generator covering all 40 versions and every error-correction level, checked against ZXing, jsQR and the qrcode npm package. EncodePng() writes a PNG with zero engine dependencies; PmcHost.QrTexture() hands you a Texture2D.

One click beyond the LAN

host.StartTunnel() fetches a checksum- and signature-verified cloudflared, opens a Cloudflare Quick Tunnel (no account), waits for DNS, then swaps the QR to an https://…trycloudflare.com URL and turns on a join code. Named tunnels supported for a stable hostname.

pmc.js controller SDK

The same zero-dependency ES module the Godot port serves, at /pmc/pmc.js. Reconnect with jittered backoff, clock sync for fair timing, vibrate() and screen-wake-lock helpers, and a saved token so a refresh keeps your seat. No build step.

Lobby helpers

PmcQueue, PmcVote (majority, vetoes, timeout) and PmcRotation (winner-stays / loser-stays / strict) — pure-logic pieces lifted out of a real party game, covered by the same NUnit suite as the core.

Unity-native, CI-friendly

A dockable Window → Phone Controllers panel shows live host status, players and a throwaway test tunnel — in Play mode and edit mode. Builds copy your controller files into StreamingAssets automatically. The engine-free core runs plain dotnet test — no Unity license needed in CI.

Which engine?

Two ports, one protocol. A Godot host and a Unity host are interchangeable to a phone: the same pmc.* messages, the same pmc.js, the same HTTP routes. They're independent implementations — not a shared codebase, not a wrapper; each one is idiomatic to its engine. Pick whichever engine your game is already in.

Honest caveats

This is a party-room host, not a service. It earns its keep on a couch, not at scale.

  • Quick-tunnel URLs are ephemeral. Every StartTunnel() gets a new *.trycloudflare.com address, free and account-less but strictly best-effort — no uptime guarantee. Great for a game night; not a hosted endpoint. For a stable https://party.example.com, use a named tunnel (TunnelMode = "named" + a Cloudflare token); Tailscale Funnel, ngrok and relay options are compared in docs/tunnels.md.
  • Tunnels are desktop-only. StartTunnel() spawns a cloudflared child process, so it works in the editor and in Windows/macOS/Linux desktop builds — not on mobile or console players, which can still host over the LAN.
  • Plain LAN http isn't a secure context. Screen wake lock and a few other web APIs need https, so on http://192.168.x.x a phone can still doze off mid-game. The tunnel URL is https and gets wake lock back.
  • iOS can't vibrate. Safari on iPhone has no navigator.vibrate; vibrate() feature-detects and quietly returns false there.
  • Backgrounded phones go quiet. Mobile browsers suspend WebSockets in background tabs and on lock screens. The SDK reconnects when the page returns, and GraceSeconds keeps the player's seat (and score) warm meanwhile.
  • Your Wi-Fi has to allow it. LAN play needs a network without client isolation — many "guest" and campus APs block device-to-device traffic, which is exactly what this is.
